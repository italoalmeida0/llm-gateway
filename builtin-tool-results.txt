*** FORMATO ATUAL (envelope pseudo-XML) — lê isto primeiro ***
Todos os exemplos abaixo mostram o TEXTO que hoje é o CORPO do envelope. Desde
a mudança de envelope, cada tool_result que o modelo recebe é:

    <tool_result type="ok" exit="0">hello\nworld</tool_result>
    <tool_result type="error">permission denied: this agent has no filesystem read permission</tool_result>

Contrato (packages/core/envelope.go + spec no system prompt):
- Corpo = SÓ conteúdo da ferramenta (output de programa, texto de arquivo,
  linhas de log). Metadado do sistema nunca vai no corpo — vai em atributos:
  exit, status, page, next, truncated, job_id, info, duration, total, ...
- type="error" é a ÚNICA exceção: corpo = mensagem de erro do sistema, e é
  usado SÓ quando a CHAMADA falhou (argumento inválido, permission denied,
  not found, abort). O exit≠0 de um comando NÃO é error: é type="ok" exit="2".
- "<tool_result" literal no output é escapado como "&lt;tool_result".
- Wrap centralizado: core.WrapToolResultContent (packages/core/envelope.go),
  aplicado em core/agent.go runOneTool (choke point único). As tools só
  preenchem Content (corpo puro) + Attrs (fatos).
- Frontend faz strip das tags na renderização (web/src/indirect-code/utils/
  envelope.ts) e guarda os attrs em toolDetails.env para os rótulos da UI.
- Migração v3 (internal/migrations/v3_tool_result_envelope.go) envelopa os
  tool_results legados dos JSONL de sessão; is_error vira type="error".

Onde os exemplos antigos abaixo viram atributos (mapeamento):
- bash "Command exited with code N"  -> exit="N" (type=ok!) + corpo = output
- bash/python "Command aborted/stopped" -> status="aborted|stopped"
- bash/python "[Showing lines X-Y of N]" -> page="X-Y/N" truncated="true" next="Y+1"
- read "[Showing lines ... Use offset=N]" -> page= + next= + truncated=
- read "[Line N is X; showing first Y]" -> line= line_size= shown= next_byte=
- read "[N more lines in file]" -> page= + next=
- glob/search "(Truncated: showing first N)" / "(capped at N …)" -> truncated="true"
- glob/search "(no matches)" / "No files matched" -> info="no matches" (corpo vazio)
- bg_check "No output yet." -> info="No output yet." (corpo vazio — seu caso!)
- bg_check "Background Task (%s) — %s" + "Command:" + "Status:" -> kind= status= command= exit=
- bg_check "Lines X–Y of N (D dropped)" + "[N more lines…]" -> page= dropped= next=
- write/edit "Successfully wrote/replaced …" -> info= (corpo vazio)
- python "[exit N]  Took X" -> exit="N" duration="X" (corpo = stdout+stderr)
- python "(no output)" -> info="no output"
- bg_await "Waited X." / "Woken early…" / "[Note: …]" -> status= waited= info=
- completion "Task marked as complete." -> info= (corpo vazio)
- fetch_url "fetched URL" + "…(truncated, N chars)" -> url= chars= truncated=
- web_search "(cached)" / "N results for Q" / "(no results)" -> cached= query= total= info=
- inspect "(N entries, capped at M)" -> total= truncated= info=
- todo JSON continua no corpo (é dado), done/total/progress viram attrs.


HOW RESULTS REACH THE MODEL (envelope)
--------------------------------------
- Tool.Execute returns core.ToolResult { Content []provider.Content, IsError,
  Details any } — indirect-code-daemon/packages/core/tool.go:27-40.
- The agent wraps it as provider.ToolResultBlock{CallID, Content, IsError} in a
  RoleTool message — packages/core/agent.go:1052-1060.
- IMPORTANT: when Execute returns a Go error, the model sees ONLY the error
  string as tool_result text with IsError=true (agent.go:1149-1150). The
  "invalid args: " / "Could not edit file:" prefixes below are part of that
  string. Details/display never reach the LLM (UI-only).

ANTHROPIC MESSAGES API — REQUEST ENVELOPE (what the model receives, in general)
================================================================================
When the model "receives" a tool result, it is never a standalone payload: it is
one block inside the messages array of a full Messages API request. Everything
below travels on every request.

Top-level request fields (Anthropic spec)
-----------------------------------------
    {
      "model": "claude-sonnet-4-5-20250929",
      "max_tokens": 8192,              // required
      "system": "…" | [ {type:"text", text, cache_control?} ],
      "messages": [ ...full conversation history... ],
      "tools": [ {name, description, input_schema, cache_control?} ],  // resent every request
      "tool_choice": {"type": "auto"|"any"|"tool"|"none", ...},
      "temperature": 1,
      "stream": true,
      "metadata": {"user_id": "…"},
      "stop_sequences": ["…"],
      "thinking": {"type": "enabled", "budget_tokens": N}
    }

The tool_use → tool_result pairing
----------------------------------
Assistant turn (previous) carries the request:
    {"role": "assistant", "content": [
        {"type": "text", "text": "Vou ler o arquivo…"},
        {"type": "thinking", "thinking": "…", "signature": "…"},
        {"type": "tool_use", "id": "toolu_01ABC…", "name": "read", "input": {"path": "a.txt"}}
    ]}
User turn carries the reply:
    {"role": "user", "content": [
        {"type": "tool_result",
         "tool_use_id": "toolu_01ABC…",     // REQUIRED — pairs with the tool_use
         "content": "…" | [ {type:"text"| "image", …} ],   // string or rich blocks
         "is_error": false}                 // optional flag
    ]}

What travels WITH the tool content
----------------------------------
- tool_use_id: the pairing key; mismatch = API 400 error.
- is_error: boolean error flag.
- content can be rich: array of text AND image blocks (e.g. read of an image
  returns tool_result with an image block).
- tool name + input are NOT in the tool_result — they live in the assistant's
  tool_use block, still present in history.
- the full tools[] (name/description/input_schema) is resent every request —
  this is what consumes the prompt cache prefix.
- system prompt + entire history: tool_result is just one block in the stream.

Model response side
-------------------
    {
      "id": "msg_…", "type": "message", "role": "assistant",
      "content": [ {"type":"text",…}, {"type":"tool_use",…} ],
      "model": "…",
      "stop_reason": "tool_use",   // end_turn|max_tokens|stop_sequence|tool_use|pause_turn
      "usage": {
        "input_tokens": 1200,
        "output_tokens": 85,
        "cache_creation_input_tokens": 0,
        "cache_read_input_tokens": 1180
      }
    }

Streaming events carrying it
----------------------------
message_start → content_block_start (block: tool_use|thinking|text) →
content_block_delta (input_json_delta|text_delta|thinking_delta|signature_delta) →
content_block_stop → message_delta (stop_reason + final usage) → message_stop.
NOTE: final usage arrives in message_delta, not message_start.

What OUR daemon sends (subset)
------------------------------
model, max_tokens, system, messages, tools, temperature (omitted for reasoning
models), stream:true. anthToolResultBlock has only type, tool_use_id, content,
is_error, cache_control (packages/provider/anthropic.go:95-102).
We do NOT send tool_choice, metadata, stop_sequences or thinking today.
